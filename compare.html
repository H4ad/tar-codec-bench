node-tar vs tar-codec

Astral's Rust tar parser extracts npm-shaped tarballs with hundreds to thousands of entries 5.3 to 7.8 times faster than node-tar once both sides restore file modes and mtimes, and 4.2 times faster end to end on an install-shaped run. Peak memory for a 10k-entry archive is +2 MB against +191 MB. It still cannot replace node-tar in npm without eight gaps and a native build for every platform. Measured through a napi addon, against the real tarballs npm ships.

Where node-tar spends the time

Same 1051-file tree written by a plain fs.writeFileSync loop: 14.7 ms. tar-codec extracts in 10.1 ms, so it sits at the filesystem floor on this work dir (tmpfs). node-tar takes 79.2 ms, which is per-entry stream and callback work, not I/O. Because tar-codec is at the floor, the ratio shrinks on a slower filesystem; set TAR_BENCH_WORK to a directory on a real disk and rerun to see the disk-bound number.

130 packages is about 0.32 s of extract work in node-tar at 8 in flight, against 0.08 s for the best tar-codec arm. Every arm writes the same paths and bytes (the codec arms strip package/ with a staging dir and a rename, since tar-codec has no strip option) and each run is checked against the tar-1 tree. On a 500-package cold install that is a couple of seconds, not a different install.

The concurrent rows chart the async arm, because a blocking napi call cannot overlap: eight of them run one after another in a single tick. On the 10k archive the blocking call peaks at +2 MB, against +183 MB for the async arm that actually overlaps, and node-tar peaks at +1028 MB holding eight in flight. The async wrapper copies the archive per task, which is most of its peak; that copy is avoidable by sharing the buffer or reading from a file handle. Peak ranges across 3 runs: node-tar 1099 to 1107 MB, tar-codec 254 to 255 MB. The chart is peak over idle, not the retained delta after the directories are removed.

The fidelity test is a pax tarball with a 0600 file, a 0700 file, an mtime from 2020, a symlink and a hard link. node-tar restores all of it. tar-codec writes 0644 and 0755, stamps the current time, creates the symlink, and aborts on the hard link, leaving a partial tree. Vendor records matter for the same reason strictness helps: a tarball made by macOS or bsdtar carries SCHILY and LIBARCHIVE records, which the default policy rejects. An allowlist fixes it, and that path is tested.

05

Verdict

The speed is real and it is at the filesystem floor. The reason not to ship it yet is semantics, distribution and the missing writer, in that order.

What tar-codec buys

5.3 to 7.8 times the extract throughput on packages with hundreds to thousands of files once both sides restore modes and mtimes, and 7.6 to 10.7 times when tar-codec's own output semantics are accepted. No heap growth, and a parser that rejects the family-mixing and tombstone tricks the blog post describes.

What it costs

A native build matrix, a fallback path, a second wrapper for pack and publish, and eight gaps: four fidelity changes users would notice in modes, mtimes, links and vendor records, plus strip, filter, mode metadata and a writer.

If it were my call

  • Prototype inside pacote behind an env flag, not in the CLI.
  • Fix the gaps in the wrapper first: modes, mtimes, hard links, vendor allowlist, strip.
  • Measure a real npm ci before committing to prebuilds.

Method

h4ad (AMD Ryzen 9 5950X 16-Core Processor, 32 threads), tmpfs work dir, linux x64. v24.20.0, node-tar 7.5.22, tar-codec 0.0.15. Work dir /tmp/tar-codec-bench-work on tmpfs. Every number on this page is read from results/*.json, written by the benchmark that produced it; npm run all reruns the set and regenerates this page. Corpora: lodash, typescript and eslint pinned in fetch-corpus.js, two generated pax tarballs, and a real dependency closure pulled from the registry. The addon is a napi-rs cdylib over tar-codec 0.0.15 with flate2/zlib-rs for the gzip arm; source and scripts sit next to this page. Absolute times on tmpfs will be lower than a real disk, and because tar-codec runs at the write floor the ratio shrinks on a slower filesystem.
