node-tar vs tar-codec

Astral's Rust tar parser is 7 to 11 times faster at extracting npm-shaped tarballs, needs 1 MB of resident memory instead of 190, and still cannot replace node-tar in npm without four behaviour changes and a native build for every platform. Measured through a napi addon, against the real tarballs npm ships.

Where node-tar spends the time

Same 1051-file tree written by a plain fs.writeFileSync loop: 15.3 ms. tar-codec extracts in 10.3 ms, so it sits at the filesystem floor. node-tar takes 88.7 ms, which is per-entry stream and callback work, not I/O. That is why the ratio survives on a real disk, and why the 53-entry corpus with 200 KB files shows no win at all.

Install-shaped: real dependency closure of eslint, express, typescript, webpack and jest, 130 packages, 4313 files, 32 MB unpacked. Median of 4.

130 packages is about 0.50 s of extract work in node-tar at 8 in flight, against 0.11 s for the best tar-codec arm. On a 500-package cold install that is a couple of seconds, not a different install.

The async wrapper (needed so pacote can keep eight extractions in flight) costs one copy of the archive per task: +65 MB at 8 concurrent 10k-file archives, against +2 MB for the blocking call. That copy is avoidable by sharing the buffer or reading from a file handle. The 1101 MB node-tar figure is not a typo: eight concurrent unpacks of a 10102-entry archive hold roughly a gigabyte of live stream buffers.

The fidelity test is a pax tarball with a 0600 file, a 0700 file, an mtime from 2020, a symlink and a hard link. node-tar restores all of it. tar-codec writes 0644 and 0755, stamps the current time, creates the symlink, and aborts on the hard link, leaving a partial tree. Vendor records matter for the same reason strictness helps: a tarball made by macOS or bsdtar carries SCHILY and LIBARCHIVE records, which the default policy rejects. An allowlist fixes it, and that path is tested.

05

Verdict

The speed is real and it is at the filesystem floor. The reason not to ship it yet is semantics, distribution and the missing writer, in that order.

What tar-codec buys

Seven to eleven times the extract throughput on packages with hundreds to thousands of files, with no heap growth and a parser that rejects the family-mixing and tombstone tricks the blog post describes.

What it costs

A native build matrix, a fallback path, a second wrapper for pack and publish, and four behaviour changes that users would notice in file modes and mtimes.

If it were my call

  • Prototype inside pacote behind an env flag, not in the CLI.
  • Fix the gaps in the wrapper first: modes, mtimes, hard links, vendor allowlist, strip.
  • Measure a real npm ci before committing to prebuilds.

Method

Ryzen 9 5950X, 32 threads, tmpfs, Linux x64. node v24.20.0, node-tar 7.5.22, tar-codec 0.0.15. Medians of 7 for raw tar, 5 for .tgz, 4 for the install closure, 3 process runs for memory. Corpora: lodash 4.18.1, typescript 7.0.2, eslint 10.13.0, two generated pax tarballs, and the latest versions of a real dependency closure pulled from the registry. The addon is a napi-rs cdylib over tar-codec 0.0.15 with flate2/zlib-rs for the gzip arm; source and scripts sit next to this page. tmpfs absolutes will be lower than a real disk; ratios track per-entry cost, not I/O.
